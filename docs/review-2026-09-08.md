## 已修复：四类边界问题

### 1. 候选评分与真正提交的状态不一致

原 `evaluate_rewrite_candidates` 用列表拼接计算候选熵，但引擎通过 `CognitiveState.with_added` 按 ID 去重。`AtomFactory` 每次从 `rw_*_1` 开始，不避开现有 ID。存在重名时，评分包含了一个实际上不会加入状态的原子。

回归用例中，旧代码预测总熵约为 `0.10`，对真正提交的状态重算却为 `0.60`。

修复：工厂保留现有及已提出原子的 ID；评分直接使用与引擎一致的 `with_added` 集合扩展。未改变无冲突情况下的确定性 ID 顺序。

### 2. 容量折叠循环读取旧内存视图

原 `_fold_once` 追加写回原子及 overlay 后，没有刷新 `_all`。下一次迭代可能再次选择同一对原子，因生成相同 ID 而退出，即使有效成本仍超预算。

修复：抽出 `_refresh_atoms`，每次折叠后刷新合并视图，不提前从磁盘重载未持久化的数据。四个成本为 1 的原子，在折叠比例 0.5、有效预算 1 的测试中完成三次折叠，并保留所有原始原子。另覆盖最大迭代数、禁止 seed overlay 和重载后的行为。

注意：这里降低的是 `effective_cost`，不是物理存储大小；没有将 No-DROP 改成删除。`cost_mode=total` 的容量语义仍需另外设计，不能把本修复解读为保证所有配置都达到预算。

### 3. 同一次成功调用被重复计为多次验证

原 `write_back` 对列表中每次出现的内容都累加计数；两个 ID 不同但内容相同的候选，也能在一次调用中达到 `min_successes=2`。重复项还会挤占不同候选的数量限额。

修复：先按内容指纹去重，再应用 `max_atoms_per_run`，每个指纹每次成功调用只计一次。

这没有实现跨重试的 run ID 幂等，也没有解决多进程共享 JSON 文件时的并发事务问题。

### 4. 生成原子被当作外部证据

原 `_is_non_generated` 会信任非字符串的 `rewrite_type`；丢失该字段的 `BRIDGE:`、`ABSTRACT:`、`CONSTRAINT:` 文本也会被计入非生成证据。此外，必需 claim key 从整个状态收集，生成原子的元数据能够补齐一个缺失事实键。

修复：非生成证据检查同时识别文本标记和合法元数据；必需 claim key 仅从同一非生成证据集合收集。

这是有意收紧的验证器边界：生成结构不能仅靠自己声明的字段证明外部事实存在。验证器关闭时的行为未变。它不是来源认证或完整事实真伪判定；未来合法推导结果如何经独立验证进入证据集合，仍是待讨论问题。

## 未修改：更值得检验的研究问题

### A. 严格降熵是否对应新增的可用证据？

代码观察：`rewrite.py` 的 bridge 可以复制查询向量，或把问题复述进文本；它不必获得新事实就能降低覆盖项。constraint 为冲突对写入 `reconcile_pairs` 后，`entropy.py` 的 `chi` 即认为该对不再冲突，并不要求给出裁决理由或独立验证。`engine.py` 的历史成功信号来自本身的门控通过，而不是下游答案正确性或外部任务结果。

审查判断：目前严格下降约束证明的是“给定打分函数下的状态转移”，不自动证明知识增加、事实正确或认知不确定性已校准。

候选实验：区分结构性覆盖与证据支持；比较有无独立冲突裁决时的结果；把门控通过率与外部任务正确率分别记录。是否需要调整熵定义或添加新的证明义务，尚未确定，本补丁没有替换原公式。

### B. 当前 100/100 能支持怎样的结论？

代码观察：`data/tasks_pitfalls_100.json` 明确通过逐题 `task_overrides.verifier.required_claim_keys` 提供事实键。`baseline_pack.py` 的提示只有问题和记忆 ID/文本，没有把这些字段同等提供给基线。`eval.py` 对核心检查整个最终状态中的 ID，而基线需要自行选择并输出 `used_ids`。其 `baseline_safety_pass_rate` 衡量是否与核心初始门控一致，而非独立定义的现实安全结果。

这仍是有价值的受控结构测试，但不是等信息、等任务条件下的通用推理能力比较。本次保留该基准用于回归，不修改历史成绩或将其解释成更广泛的结论。

候选实验：设置等信息与无逐题事实键两种条件；所有方法采用同一决策/引用输出和评分；比较 S1+V、S1+熵门控+V、完整 S2、同证据的 LLM+V；增加非同模板的留出任务，分别报告错误回答和过度拒答。

核心待回答问题：排除人工要求字段和验证器规则的贡献后，S2 提供了多少可独立测量的增益？

### C. 持久化是否保持记忆表示与依赖关系？

代码观察：`save_memory_file` 不保存向量，`load_memory_file` 总是从 `v_i` 重新生成向量。然而 abstraction/fold 的初始向量来自源向量平均，文本通常仅包含被组合的 ID。写回后重载可能改变向量及检索行为。运行时 ID 改成稳定写回 ID 时，引用其他生成原子的 `subsumes` / `reconcile_pairs` 也没有统一重映射。

候选处理：先定义版本化表示与依赖的持久化契约，再补充向量、检索和引用完整性的 round-trip 测试；可比较保存推导配方后重建与保存带版本向量两种方案。本次未变更存储格式。

### D. 其他工程边界

`embedding.py` 仅提取 `[a-z0-9]+`，纯中文输入没有有效 token；任务文件也声明了这一限制。支持中文需要明确 tokenizer/embedding 版本，避免静默改变参考基准。

配置中的布尔强制转换、非法数值、历史文件格式、JSON 持久化的原子性与并发隔离、基线缺失输出的分母及格式校验，也值得后续检查。这里只记录代码层面可见的风险，尚未进行完整并发、负载或故障注入测试。
